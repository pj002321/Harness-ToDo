# 설계 근거

## 하네스란

모델 바깥에서 모델의 일을 **구조로 통제하는 코드**. 프롬프트가 "부탁"이라면 하네스는 "환경"이다.
이 저장소에서 하네스가 쥐고 있는 것은 네 가지다.

| 하네스가 쥔 것 | 어디서 | 모델에게 맡기면 생기는 일 |
|---|---|---|
| **순서** — 누가 언제 일하나 | `harness/run.js` | 계획 없이 바로 코딩, 범위 축소 |
| **권한** — 누가 무엇을 할 수 있나 | `agents.js`의 `*_TOOLS` → `claude -p --tools/--allowedTools` | 평가자가 직접 코드를 고쳐 통과시킴 |
| **출력 모양** — 무엇을 넘겨주나 | `--json-schema` | 파싱 실패, 애매한 "대체로 됨" |
| **판정** — 언제 끝났나 | `evaluate()`의 pass 계산, `MAX_ATTEMPTS` | 자기 결과물 과대평가, 무한 루프 |

## 원문 구조와 이 저장소의 대응

원문(Anthropic, 2026-03)은 생성자/판별자를 분리한 GAN에서 착안해 세 에이전트를 썼다.

- **Planner** — 1~4문장 요청을 야심찬 제품 스펙으로. 구현 세부는 정하지 않는다(잘못 못박으면 오류가 전파됨).
  원문 V2에서 다른 부품을 걷어낼 때도 Planner는 남았다: 없으면 Generator가 범위를 줄인다.
- **Generator** — 스프린트 단위로 구현. 시작 전에 Evaluator와 **Sprint Contract**(이번 스프린트의 완료 정의)를 협상.
- **Evaluator** — 실행 중인 앱을 직접 조작해 계약 항목별 pass/fail. 원문에서 가장 튜닝이 어려웠던 부품
  (버그를 찾고도 "사소하다"며 통과시키는 경향).

| 원문 | 여기 |
|---|---|
| Claude Agent SDK, React/Vite/FastAPI/SQLite | `claude -p` 프로세스, Node 표준 라이브러리만 |
| Evaluator가 Playwright로 클릭 | Evaluator가 `curl`로 호출 + 코드 읽기 (화면 동작은 코드로 판단) |
| 파일로 에이전트 간 통신 | 동일 — `runs/<id>/` |
| 수 시간, 수백 달러 | ToDo 규모로 축소 — 체험 가능한 크기 |

## 결정과 이유

**에이전트 1명 = `claude -p` 프로세스 1개.** API 키 없이 각자의 Claude Code 로그인으로 돌아가고,
CLI 플래그만으로 권한을 다르게 줄 수 있다. 매 호출이 새 세션이라 "컨텍스트가 차서 흐트러지는" 문제가 구조적으로 없다 —
대신 필요한 맥락(스펙, 계약, 직전 판정)을 하네스가 매번 프롬프트로 넣어준다(원문의 context reset + 구조화된 인계).

**앱은 하네스가 띄운다 (`app.js`).** Evaluator에게 서버 기동까지 맡기면 "서버가 안 떠서 검증 못함"과 "기능이 틀림"이 섞인다.
기동 실패는 LLM을 부를 것도 없이 하네스가 즉시 전부 FAIL 처리한다.

**합격은 하네스가 계산한다.** Evaluator는 항목별 `{id, pass, evidence}`만 낸다. 계약의 id 중 하나라도 pass가 아니면(빠뜨린 것 포함) FAIL.
"전반적으로 훌륭합니다" 같은 말로 통과시킬 수 없다.

**개인 설정 격리 (`--setting-sources ''`, `--strict-mcp-config`).** 실행하는 사람의 CLAUDE.md·훅·MCP가 섞이면
사람마다 결과가 달라진다. 하네스의 조건은 코드에 있는 것이 전부여야 한다.

**solo와 harness를 같은 숨겨진 기준으로 채점.** `acceptance.json`은 Generator에게 보여주지 않는다.
하네스 쪽 Generator는 자기 계약을 통과했어도 최종 심사에서 떨어질 수 있다 — 그것도 그대로 보여준다.

## 일부러 뺀 것 (그리고 언제 넣을지)

- **Playwright UI 검증** — 설치가 무겁다. 화면 상호작용 버그를 잡아야 할 만큼 앱이 커지면 Evaluator 도구에 추가.
- **병렬 스프린트, worktree 격리** — ToDo 규모에선 순차가 충분하고 보기 쉽다.
- **Prometheus/Terraform 등 운영 스택** — 초기 스캐폴드에 있었지만 동작하지 않는 틀이라 제거.
  하네스의 "관측성"은 `events.jsonl` + 뷰어가 담당한다.

## 원문의 마지막 교훈

> 하네스의 모든 부품은 "모델이 혼자서는 못 하는 것"에 대한 가정이다. 모델이 좋아지면 그 가정은 낡는다.

그래서 부품을 하나씩 빼보며 실제로 하중을 받는지(load-bearing) 확인해야 한다.
이 저장소에서 해볼 수 있는 실험: 계약 협상 생략, `MAX_ATTEMPTS = 1`, Evaluator 프롬프트를 관대하게 —
각각 뷰어에서 최종 심사 결과가 어떻게 바뀌는지 본다.
